# Streams

Streams plays games running on another computer. It is a GameStream client: the host runs [Sunshine](https://github.com/LizardByte/Sunshine) (or NVIDIA GameStream), and Nokcandu pairs with it, starts an app on it, and shows its video and sound while sending this Mac's keyboard, mouse and controllers back. The streaming side is ported from [VoidLink](https://github.com/The-Fried-Fish/VoidLink-previously-moonlight-zwm) (Integration branch), a Moonlight fork, and its streaming core.

Status as of November 13, 2026: **streams from a Sunshine PC with picture, sound, mouse and clicks.** See [What is verified](#what-is-verified) and [Fixes found with a real host](#fixes-found-with-a-real-host).

### Why not the keychain

URLSession and Network.framework need a `SecIdentity` for a client certificate, which on macOS means importing the key into a keychain. Doing TLS with Mbed TLS keeps the identity in two files (`Application Support/Nokcandu/Streams/client.pem`, `client.key`, mode 600) and avoids keychain prompts. Hosts use self-signed certificates, so trust comes from pinning the certificate received while pairing: an HTTPS answer from any other certificate is refused (`NK_HTTP_ERR_PINNED`).

## How a stream runs

1. **Pairing** (`StreamClient.pair`, VoidLink's `PairManager`): the Mac shows a four-digit PIN to type on the host's Sunshine web page. Five steps: send our certificate with a salt (the host answers once the PIN is typed, up to two minutes); exchange encrypted challenges with a key from SHA-256(salt + PIN) (SHA-1 for hosts older than GameStream 7); check the host's signature and that its hash proves it knows the PIN; send our signed secret; confirm over HTTPS. A wrong PIN is caught before our secret is sent.
2. **Launch**: `/launch` (or `/resume` when the app is already running) with resolution, frame rate, the remote-input key, HDR, audio layout and controller mask. Another app already running is quit first.
3. **Connect**: `LiStartConnection` with the stream configuration. Codecs offered: H.264 always; HEVC when the Mac decodes it in hardware and the host encodes it; AV1 likewise (M3 and later); 10-bit with HDR on; 4:4:4 when chosen. A chosen codec removes the fallbacks.
4. **Video**: Annex B NAL units become length-prefixed samples; parameter sets on key frames make the format description; a hardware `VTDecompressionSession` decodes; frames go to an `AVSampleBufferDisplayLayer`. Pacing: *Lowest latency* shows each frame at once; *Balanced* shows the newest on the next display refresh (`NSView.displayLink`); *Smoothest* keeps one in reserve. A decode error asks the host for a key frame.
5. **Audio**: Opus packets decode into a ring buffer that an `AVAudioSourceNode` drains, with at most 60 ms kept so sound stays in step.
6. **Input**: keys as Windows virtual keys (`0x8000 | vk`, as VoidLink does), ⌘ as the Windows key unless turned off; captured mouse movement (pointer frozen with `CGAssociateMouseAndMouseCursorPosition`, mouse coalescing off for every report) or absolute pointer position; high-resolution scrolling (120 per notch).
7. **Controllers**:
   - *Controller as it is*: each GameController controller is announced to the host with its type (PlayStation, Switch or Xbox, or as chosen) and capabilities, then sent on every change. Host rumble, motion requests and light colours go back to it.
   - *A Nokcandu profile*: while the stream window is the key window, `DesktopPad` uses the stream's profile and routes everything it outputs to the stream instead of the Mac: the mapped controller as player one, keys, mouse buttons and movement, scrolling and typed text. This is the full profile — layers, gyro aiming, Steam Controller trackpads, radial menus. "Keys and mouse only" sends no controller at all. Accessibility permission isn't needed for this, as nothing is posted to macOS.

Shortcuts during a stream: ⌃⌥⇧Q ends it, ⌃⌥⇧Z frees or captures the pointer, ⌃⌥⇧X switches full screen, ⌃⌥⇧S cycles the statistics, ⌃⌥⇧D minimises.

## What is verified

Verified on November 13, 2026 (tests in `Tests/NokcanduCoreTests/StreamTests.swift`):

- Identity generation, signing and verification with PEM and DER certificates; the private key is written with mode 600 and reused.
- AES-128-ECB against the FIPS-197 test vector.
- Pairing steps 1–4 against a fake host that does the host's half of the exchange, with the right PIN (the host verifies our signed secret and hash) and a wrong PIN (refused before our secret is sent). Step 5 (HTTPS) is not covered by a test.
- Parsing Sunshine's server info and app list (including the mislabelled UTF-16 header), error status, addresses (IPv4, IPv6, ports, private ranges including Tailscale's), merging a typed host into its real ID with its profiles, unpairing a host that forgot us only when HTTPS says so.
- AV1 sequence header parsing and the `av1C` box from a synthesised 10-bit BT.2020 PQ header.
- The HTTP client with Content-Length, chunked and closed-connection answers.
- The app builds in release; all 698 Swift tests and the build-script tests pass.

Verified with the user's Sunshine host: pairing, HTTPS, launch and resume, AV1 1080p60 video, mouse and clicks, Bonjour discovery, and audio packets decrypting after the padding fix.

**Not yet verified**: sound heard by the user after the fix, keyboard typing, HDR, 4:4:4, H.264/HEVC on this Mac, Wake-on-LAN, rumble and motion, profile passthrough during a stream, VBAN with VBAN Receptor.

## Fixes found with a real host

Found on November 13, 2026 while streaming from the user's Sunshine PC.

- **The app froze during a stream** (no clicks, no keyboard, no way to end it, while the video kept playing). A sample of the hung process showed the main thread's display refresh waiting on the decoder's lock. The decoder thread held that lock while calling `VTDecompressionSessionDecodeFrame`, which can wait for VideoToolbox's output handler, and the handler took the same lock. Finished frames and the key-frame flag now have their own lock, which the output handler and the display refresh use; the decoder lock is only used on the decoder thread.
- **No sound**: every audio packet logged "Failed to decrypt audio packet". Mbed TLS 3 no longer sets a default padding mode in `mbedtls_cipher_setup`, and moonlight-common-c's Mbed TLS code was written for 2.x, so every AES-CBC `finish` failed. Audio is the only stream that uses AES-CBC (control and input use AES-GCM), which is why picture and input worked. The core now sets PKCS #7 padding for decryption and none for encryption (it pads itself), matching OpenSSL. Test: `StreamCoreCryptoTests` against NIST SP 800-38A.
- **Keyboard and mouse**: input is taken by a local event monitor on the stream window rather than relying on its first responder (the overlay's buttons could take focus). The user confirmed the mouse and clicks work.
- **A pairing was erased by a failed check.** A host whose secure port took connections but never finished the handshake (`TLS -0x6800` timeout in the log; it recovered after restarting Sunshine) was treated as "unpaired" and its certificate deleted. Saved pairings are now never dropped automatically: only the user removes a host or pairs again. A host that still knows this Mac is reconnected without a PIN (`StreamClient.recoverPairing`: HTTPS with our certificate, accepted only when it answers that we are paired). A stuck secure port now says to restart Sunshine.
- **No way out**: a **Stream** menu (Show Stream, Free or Capture the Pointer ⌃⌥⇧Z, End Stream ⌃⌥⇧Q, End and Quit the App) and the menu bar icon's menu can end a stream.
- **No controller**: "Emulated controller type → No controller" sends none; a Nokcandu profile's keys, mouse and scrolling still go to the host.
- The log is `~/Library/Logs/Nokcandu/Streams.log` (host checks, pairing failures, TLS codes, the core's messages, the first input events).

- **Sunshine's secure port stuck after Nokcandu was killed mid-stream** (twice on November 13, 2026: the frozen copy force-quit, then an install that killed Nokcandu during a stream). Afterwards the host's HTTPS port (47984) accepts connections but never completes the TLS handshake (`TLS -0x6800` timeout), so pairing, launch and quit fail until Sunshine is restarted; plain HTTP keeps answering. Whether this is Sunshine's bug or something the abandoned session left is not known. Nokcandu now ends a running stream properly when it quits (`StreamsModel.endStreamForQuit`, up to 3 s), and development installs must not kill Nokcandu during a stream. The host is Apollo (it offers "Virtual Display"). Other clients that vanish don't do this, so something Nokcandu's session does is suspected; not yet known what. Nokcandu-specific traffic on that port during a stream was removed while this is open: host checks now pause during a stream (as in Moonlight), and automatic clipboard sync (Apollo's `/actions/clipboard` on every focus change) is off by default. Next evidence needed: Apollo's log (`sunshine.log` in its config folder, or the web page → Troubleshooting) from the minutes before it stopped answering.
- **Settings changed during a stream** were saved but not applied (found when VBAN was switched on mid-stream and nothing was sent). The stream window now keeps the current profile and applies what can change live (`StreamWindowController.apply`): volume, VBAN, frame pacing, statistics, full screen, mouse mode, scrolling, key options, clipboard, and the controller settings (the host sees the controllers leave and arrive again). Resolution, frame rate, bitrate, codec, HDR, colour, channels, sound on the host, the app and the route apply from the next stream; the editor says so while streaming.

- **No stream sound** (November 13, 2026): audio decoded normally (peaks around −3 dBFS), but the Mac's default output was a virtual device ("Jump Desktop Microphone"), and the playback engine was also found stopped. The user switched the output to the MacBook Air speakers, which brought the sound back. Nokcandu now restarts its output when macOS reports an audio setup change (`AVAudioEngineConfigurationChange`, for example another engine in the app starting its microphone, as VBAN does) and checks it every 5 s, and the log records the output device, decoded packets, failures, level and queue every 5 s. If a stream is silent, check the log's "playing to" device first. Sound → **Play on** picks an output for the stream (a Core Audio device UID per stream profile); left on "The Mac's default output" it follows macOS's default, moving when that changes (a property listener on the default output device), and a chosen output that isn't connected falls back to the default. It can change mid-stream.

- **Picture inset on a MacBook with a notch** (November 13, 2026): "This Mac's display" asked for the whole screen (2940×1912), but a full-screen window stops below the camera housing, so the picture was letterboxed. It now asks for the usable area: the screen minus `safeAreaInsets.top` in full screen, the window's content size otherwise.
- **Bitrate, frames to buffer, Game Mode**: the bitrate slider is always shown (Automatic shows the value it would use); **Frames to buffer** (0–4, or Automatic from frame pacing: 0, 1, 2) holds decoded frames for the display's refreshes, showing a frame anyway once it has waited its buffer time so a still desktop isn't held back; Nokcandu declares `LSApplicationCategoryType` games and `LSSupportsGameMode`, so macOS turns Game Mode on for a full-screen stream (macOS decides; apps can't switch it on directly).

## VBAN microphone

A stream profile can also send this Mac's microphone over [VBAN](https://vb-audio.com/Voicemeeter/vban.htm), like VBAN Talkie, for VBAN Receptor or Voicemeeter on the PC (its own **Microphone (VBAN)** section → "Send the microphone"). It runs while the stream does. Settings: microphone (Core Audio device), receiver address (the stream's host by default) and port (6980), stream name (default `Stream1`), mono or stereo, sample rate. Packets are VBAN's 28-byte header (`VBAN`, sample-rate index, samples − 1, channels − 1, 16-bit PCM, 16-byte name, frame counter) and 256 samples of little-endian 16-bit PCM per channel (`VBANPacketizer`, tested in `VBANTests`). Verified November 13, 2026 that it sends: a stream's log showed mono 24 kHz "Stream1" to the host at exactly the expected rate (10,790 packets in 115 s), and VBAN Receptor received it once its *IP Address From* and *Stream Name* matched (it plays only a matching sender, and doesn't find new ones itself). Receptor then showed Overload and Underrun with no level.

Since then, to match VBAN Talkie: packets are sent on a steady clock (macOS delivers microphone audio in ~100 ms chunks; sending each chunk as a burst under- and overran the receiver), with a short backlog that drops the oldest audio rather than build delay; packet size is selectable (64, 128 or 256 samples: "Lowest latency", "Fast", "Steady"); the microphone goes through `VBANProcessor` (equalizer: low shelf 150 Hz, peak 1.5 kHz, high shelf 5 kHz, ±12 dB; gain −12…+24 dB; noise gate opening between −70 and −30 dBFS; compressor with threshold −10…−40 dBFS, ratio 1.5…6 and make-up gain; limit at −0.2 dBFS; `VBANProcessorTests`); mute (⌃⌥⇧M, Stream menu) and push-to-talk (a chosen key or mouse button, working in any app through a global monitor and never sent to the host) send silence so the receiver stays connected; a level meter in the stream's Sound settings and an on-air icon on the stream; the log records the microphone's peak every 5 s. Processing and push-to-talk changes apply to the running sender; connection and format changes restart it. Not done: receiving a VBAN stream back (Talkie's Rx) and monitoring.

## Clipboard (Apollo hosts)

[Apollo](https://github.com/ClassicOldSong/Apollo), a Sunshine fork, shares the clipboard with its client Artemis through two HTTPS endpoints: `GET /actions/clipboard?type=text` returns the host's clipboard text as the raw body, and `POST /actions/clipboard?type=text` sets it from the raw body. Both need the client's certificate, the client's clipboard permissions in Apollo (Device Management: read clipboard / set clipboard; otherwise 401), and a running stream from that client (otherwise 403). Plain Sunshine has neither endpoint (404). Source: Apollo's `src/nvhttp.cpp`, read through a summary on November 13, 2026, not line by line, so check it there if this stops working.

With "Share the clipboard" on (Keyboard and Mouse, on by default), the Mac's clipboard text goes to the host when the stream window comes to the front (if it changed), and the host's comes back when you switch away. The Stream menu has "Send Clipboard to Host" and "Copy the Host's Clipboard". On a host without the endpoints the automatic sync stops quietly after the first 404; the menu items say why. Text only. Not yet verified against an Apollo host.

## Not ported yet

From VoidLink, still to do: Apple's low-latency frame interpolation and super resolution (macOS 26, `VTLowLatencyFrameInterpolation`; the profile settings exist but are hidden), sending the microphone (VoidLink's Sunshine build), DualSense haptics and adaptive triggers, trigger rumble, VoidLink-host extras (bitrate changes during a stream, Mac trackpad gestures), and ⌘Tab/⌘Space going to the host (needs an event tap). Left out on purpose: iOS-only features (on-screen controls, touch modes, Apple Pencil, rotation).

## Troubleshooting

- **"Couldn't reach the host"**: check the address and that Sunshine is running; it listens on TCP 47984, 47989 and 48010 and UDP 47998–48000. Over the internet those must be forwarded, or use a VPN address.
- **"The host's certificate has changed"**: the host was reinstalled or its certificate was reset. Remove it and pair again.
- **Black picture with sound**: the Mac may not decode the codec. Choose H.264 in the stream's Picture settings; check the log lines starting "Video:".
- **Pairing stops at the secure check**: the HTTP steps worked but HTTPS didn't. Note the host's Sunshine version.

- **Keyboard layout** (November 13, 2026): Input → **Keyboard layout** applies a Nokcandu keyboard layout (the same Mac key remapping games use, via `hidutil`) while the stream window is in front, so the remapped keys reach the host. It defaults to the default layout chosen for games ("The default layout"); "Normal keys" sends the keys unchanged. The layout is applied when the stream window becomes key and restored when it loses focus or the stream ends (`MacGameKeys.streamFront`, which records the previous mapping like a Mac game does, so a crash is recovered the same way). It can change mid-stream. Test: `StreamKeyboardLayoutTests`.
- **Header**: a running stream shows in the toolbar's Running strip next to running games (a stream icon with the running dot). Click shows the stream; its menu has Show Stream, Show in Streams, End Stream and End Stream and Quit the App on the Host.
- **Emulated controller type** (renamed from "Controller on the host", matching VoidLink's wording): Automatic, Xbox, PlayStation, Switch Pro or No controller. Automatic sends each controller as its own kind, or as the Nokcandu profile's Emulated controller when it has one. Saved profiles keep their value (the stored key is unchanged).
- **Full screen didn't take** (November 13, 2026): a stream set to full screen opened in a window, and turning Full screen on mid-stream did nothing. `toggleFullScreen` was called straight after the window was shown, before the app was active, and macOS drops such a request (and one made during another transition) without an error. `StreamWindowController.setFullScreen` now brings the window forward, asks, and checks every 0.6 s until the window's state matches (up to 8 tries), skipping while a transition runs; the log records the result ("Window: full screen, content … pt on <display>"). Verified that the running stream window enters full screen when asked through Accessibility; the start-of-stream path is not yet confirmed on a new stream.
- **A picture inset on every side** is the window, not the stream: in a window the picture fits inside it. In full screen a 1920×1200 (16:10) picture fills a MacBook's screen below the notch (about 1470×924 pt, within a few points), but on a 16:9 display (for example 1920×1080) it has bars at the sides. Resolution → "This Mac's display" matches the display the stream plays on (Window → Display).
- **External displays** (November 13, 2026): the stream that looked inset was playing on the only display macOS reported, a 1920×1080 "EK1080T4KHR" (an HDMI dummy plug, per the user); the built-in screen wasn't listed. Stream window placement and "This Mac's display" used whichever display the window happened to open on. Window → **Display** now picks the display per stream profile (stored as the Core Graphics display UUID plus its name, `StreamDisplays`); "The display Nokcandu is on" (the default) follows Nokcandu's own window, then the pointer. A chosen display that isn't connected falls back to the default and the picker shows it as not connected. The stream opens and goes full screen there, and "This Mac's display" asks for that display's pixels (below the notch only on a display that has one). Changing it mid-stream moves the stream (out of full screen, across, back in); the picture size stays until the next stream, and moving to a display of a different shape says so. The log records the display at the start and on each move. Profiles saved earlier decode with no display chosen. Test: `StreamDisplaySettingTests`. Not yet tried with two displays connected.
