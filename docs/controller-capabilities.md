## Repeatable observation

Use Settings → General → Controller diagnostics for receipt age, readers, focus/profile/capture and Steam presence. Keep connection/model and test conditions with each result. The temporary `Tools/controller-probe` sources observe callbacks without injecting events or changing sensor activation; command-line execution observed no devices while the GUI context did, so do not treat CLI absence as incompatible hardware. The later GUI engine probe emitted no mouse output while idle; the user was unable to rotate the controller for an active check. No real-game compatibility conclusion follows from these idle observations.

## USB Pro descriptor acceptance (November 10 follow-up)

An exact USB 057e:2009 descriptor was independently inspected. Its full-state
counter/battery bytes were mislabeled as buttons, explaining stable host fields
versus hundreds of generic Windows button transitions. The shared Wine 11.0 r1
correction preserves raw packets and exposes the actual 18 buttons (reserved
bits constant) plus packed 12-bit sticks. It has bounded native DirectInput idle
acceptance and migration/Undo tests; physical button/stick calibration, Steam
protocol use, WGI, games and Bluetooth remain unverified. This supersedes only
those earlier generic connection/idle-decoding gaps, not gameplay acceptance.

## Presenting a controller as another one (Windows games)

Added November 13, 2026. A controller profile's **Emulated controller** setting (`Profile.presentAs`, inherited like other profile settings) makes games see another controller, whatever controller is held. One choice applies everywhere Nokcandu can present it: Windows games, streams, and Mac apps (below). The compiled profile (`pad-map`) gets a `present <id>` line, which the mapping engine skips. Inside the environment's controller driver, `padmap.m` answers Wine's SDL lookups (`SDL_JoystickGetVendor`, `SDL_JoystickGetProduct`, `SDL_JoystickGetProductVersion`, `SDL_JoystickName`, `SDL_GameControllerName`) with that controller's IDs and name, for gamepads only (SDL type game controller; wheels and flight sticks keep theirs). Wine 11's `bus_sdl.c` reads exactly those when it creates the Windows device. It is read once, when Wine first asks, so a change applies from the next start; it is off with `pad-driver-off` or with all controller profiles off.

- **Xbox controller** (045E:02EA, "Xbox Wireless Controller"): available. Wine's SDL gamepad reports are already Xbox-shaped (`hid_device_add_gamepad`, Y axes flipped to match XUSB), so the identity and the reports agree. Verified in Wine 11 (OpenUA, temporary `present xbox`): both controllers appeared as 045e:02ea "Controller (Xbox One For Windows)", usage 1:5. The helper renames only for Xbox; DualShock 4 and Switch Pro IDs come only from Nokcandu's controller driver, so with Wine 10 or the stock module those controllers stay as they are instead of getting IDs their reports don't match. Wine 10 support for the DualShock 4 and Switch Pro isn't planned (decided November 13, 2026: Nokcandu has moved to Wine 11).
- **Routing**: with an identity for Windows games, a game set to "As itself" is given Wine's SDL route (`Controllers.effective` returns Xbox for it), because the imitation is built there; "Not at all" still wins.
- **Switch Pro Controller** (057E:2009): available, emulated by Nokcandu's controller driver (`Engine/controller-hid/controller-emulation.h`, wired in by `0004-controller-emulation.patch`). When `nokcandu_presented_controller` (exported by the helper) says 3 for an SDL game controller, the driver creates a raw HID device with the Pro's descriptor (the full-state variant from `pro-hid-descriptor.h`, so plain HID/DirectInput parsing sees buttons and sticks) instead of Wine's generic gamepad. It sends 64-byte 0x30 full-state reports about every 8–10 ms built from the controller's events (so profile remapping applies), and answers USB commands 0x80 01/02/03 (status with type Pro and an address, handshake, high speed) and subcommands: 0x02 device info (firmware 3.72, Pro), 0x10 SPI reads from a virtual flash (factory stick calibration centred at 2048 ± 1792, IMU calibration 0x4000/0x343b, colours, stick parameters; user calibration erased), 0x03 report mode, 0x40 IMU, 0x48 vibration and the rest acknowledged. HD rumble is approximated as SDL rumble. Buttons are positional (SDL south/east/west/north = Pro B/A/Y/X; triggers past half = ZL/ZR). Like a real Pro it is HID, not XInput (`is_gamepad` false), so XInput-only games won't see it. Each imitated Pro has its own address. "As itself" would set `Devices\057e` `Hidraw`=1 and make Wine drop the SDL-created Pro, so a game with an emulated controller is given the SDL route (see Routing below).
- **DualShock 4** (054C:05C4): available, emulated the same way (`controller-emulation.h`). A DS4-shaped descriptor (report 0x01: sticks, hat, 14 buttons, counter and analog triggers in standard usages, then a vendor block), 64-byte input reports about every 4–10 ms with motion (15.17 per °/s, 8192 per g, matching its calibration), battery/cable and two touchpad fingers from SDL touchpad events; feature reports 0x02 (motion calibration, USB layout), 0x12 (address, unique per controller) and 0xa3 (firmware); output report 0x05 rumble (left strong, right weak) and light bar passed to SDL. Positional buttons: SDL south/east/west/north = cross/circle/square/triangle. HID, not XInput. Wine prefers the raw device for a real DS4's IDs; a game using a profile has `Devices\054c` `Hidraw`=0, which keeps the imitation.
- **No double input**: the imitation replaces Wine's own gamepad for that controller (the SDL device returns before Wine's generic one is made), and with a profile in use the raw copies of PlayStation, Nintendo and Steam controllers are off. Seen in Wine: with an identity on, Windows listed only the imitated controllers. (Why a real emulation and not a rename: games and SDL on Windows that support these controllers read their own report formats and send them commands, and Wine's generic reports under those IDs would be misread.)
- **Streams**: a stream with Emulated controller type set to Automatic sends the profile's identity to the host (`LI_CTYPE_XBOX`, `_PS`, `_NINTENDO`). The host creates the real virtual controller itself, so all three work there.

DualShock 4 verified November 13, 2026 the same way: both controllers appeared as "Wireless Controller" 054c:05c4, usage 1:5, 64-byte input and 32-byte output; feature 0x02 and 0x12 read back (distinct addresses); 120 input reports in about 1 s, with live sticks from the second controller; accelerometer at rest 8192 on y. Switch Pro verified November 13, 2026 inside Wine 11 (OpenUA's environment, its compiled profile temporarily given `present switchpro`, then restored byte for byte), with `Tools/controller-probe/switch-pro-windows-hid.c`: both connected controllers (a real Pro and an original Steam Controller) appeared to Windows as "Pro Controller" 057e:2009, usage 1:4, 64-byte input and output reports; each answered the USB status (type 03), handshake and device-info subcommand (ack 0x82) and sent 60 full-state reports in about 0.6 s, the Steam Controller's with live stick values. Without the line the same controllers were Wine's generic 15-byte gamepads ("Nintendo Switch Pro Controller", "Steam Controller") answering none of those. The protocol is also checked byte by byte by `Tests/BuildScripts/test_switch_pro_emulation.py`. Also verified: the compiled profile line, the engine accepting it, inheritance, old profiles decoding, and the Streams type. **Not verified yet**: an actual Pro-aware Windows program (SDL's HIDAPI driver in a game or emulator) using it, motion axes and rumble feel, and the Xbox identity in a game. A system-wide identity for Mac apps isn't possible; see the virtual-controller row above.

## Presenting a controller to Mac apps (built, waiting for Apple's entitlement)

Added November 13, 2026. The same **Emulated controller** choice applies to Mac apps. While a Mac app is in front (not a Nokcandu Windows game, whose Wine driver presents it, and not a stream), `MacVirtualControllers` makes a CoreHID `HIDVirtualDevice` (macOS 15+) with that controller's IDs, name and descriptor, sends its input reports from the profile's mapped controller output (the pad engine's controller sink, which on the Mac was otherwise unused) plus the controller's motion, answers its output and feature reports (Switch Pro handshake and subcommands, DS4 calibration/address, rumble passed to the profile's controller), and removes it when the profile stops applying. Reports and replies come from the shared core `Sources/NokcanduPadEngine/virtualpad.c` (Xbox Wireless Controller over Bluetooth 045e:0b13, DS4 054c:05c4, Pro 057e:2009), the same code the Wine driver builds in (one copy since November 13, 2026, re-verified in Wine after the merge); `VirtualPadTests` and `test_switch_pro_emulation.py` check it.

**Not available yet**: macOS refuses `HIDVirtualDevice` without the `com.apple.developer.hid.virtual.device` entitlement and kills an app that claims it without an Apple provisioning profile granting it (tested: exit 137). So the app checks its own signature (`MacVirtualControllers.entitled`) and, without the entitlement, never calls CoreHID and shows why in the profile editor. To enable it: an Apple Developer Program membership, the entitlement granted by Apple in a Developer ID provisioning profile, then `NOKCANDU_PROVISIONING_PROFILE=/path/to/profile.provisionprofile NOKCANDU_HARDENED=1 ./build-app.sh` with a Developer ID signing identity (`build-app.sh` embeds the profile and adds the entitlement only when the profile grants it, refusing otherwise).

**Unverified until then**: whether macOS's GameController framework and SDL games treat each virtual device as that controller (the Xbox descriptor follows the Bluetooth report as Linux documents it; the DS4 and Pro reports are the ones verified in Wine), input latency, and double input: the real controller stays visible to Mac games (macOS has no way for an app to hide it), so games that read every controller may see both.

### Turning it on with an Apple Developer account

The secure way: Apple grants the entitlement, and Nokcandu is signed with Developer ID and notarized. Steps, in order:

1. **Enrol** in the Apple Developer Program (developer.apple.com/programs, paid yearly) with the Apple ID you'll sign with.
2. **App ID**: in Certificates, Identifiers & Profiles → Identifiers, register the bundle ID `io.github.seastwood.nokcandu` (explicit, not a wildcard).
3. **Request the entitlement**: Apple lists `com.apple.developer.hid.virtual.device` as a capability that has to be requested for an App ID. Ask for it, explaining the use (presenting a user's own controller, remapped by their profile, as a standard gamepad). Apple decides; until it's granted the steps below can't include it.
4. **Developer ID Application certificate**: create one (Certificates → +), install it in the login keychain. Its name looks like `Developer ID Application: <name> (<team ID>)`.
5. **Provisioning profile**: Profiles → + → Developer ID, for the App ID above, with the granted capability; download the `.provisionprofile`.
6. **Build**: `NOKCANDU_SIGN_IDENTITY="Developer ID Application: <name> (<team ID>)" NOKCANDU_HARDENED=1 NOKCANDU_PROVISIONING_PROFILE=/path/to/Nokcandu.provisionprofile ./build-app.sh`. The script embeds the profile and adds the entitlement only if the profile grants it; check with `codesign -d --entitlements - build/Nokcandu.app`.
7. **Notarize** the DMG (`xcrun notarytool submit … --wait`, then `xcrun stapler staple`), so it opens without warnings on other Macs.
8. **Releases**: the release workflow signs with the self-signed "Nokcandu Signing" identity today. For Developer ID releases it needs the Developer ID certificate (.p12) and password, the provisioning profile and notary credentials (an app-specific password or an App Store Connect API key) as repository secrets, and the signing and notarization steps above.

Things to expect when switching: macOS ties privacy permissions (Accessibility, Input Monitoring, Microphone, Local Network) to the signing identity, so after the first Developer ID build Nokcandu asks for them once more. The hardened runtime (needed for notarization) must keep the helper library loadable in Wine (it's injected into Wine processes, not into Nokcandu) and Nokcandu's own launching of Wine; test a game, streams and controller profiles on the first such build before releasing it.

Then check, with the entitled build: a Mac game or `GCController` test app sees the emulated controller as that kind (Xbox is the least certain, since only its DualShock 4 and Switch Pro counterparts were verified, in Wine); rumble and motion; and double input from the real controller (macOS can't hide it from games).

### Rumble on controllers SDL can't rumble (November 13, 2026)

Wine enables rumble for a controller only when a test `SDL_JoystickRumble(0, 0, 0)` succeeds as it opens it (`dlls/winebus.sys/bus_sdl.c`), and SDL has no rumble for some controllers: the original Steam Controller's haptics are its trackpads, which SDL's driver leaves to Steam Input. So a Steam Controller passed to games as an Xbox controller never rumbled. The Wine helper (`padmap.m`) now hands Wine's driver its own `SDL_JoystickRumble`: SDL plays what it can; when SDL can't, the request (controller IDs and name, both motors, duration) goes to Nokcandu over `~/Library/Application Support/Nokcandu/controller-rumble.sock`, and the call reports success so Wine keeps rumble on. The emulated DualShock 4 and Switch Pro send their rumble through the same call, so every route and every emulated type is covered. Nokcandu (`ControllerRumbleRouter`) plays it with the controller's own haptics: the original Steam Controller as pulses on both trackpads (through Nokcandu's own connection when it reads the controller, otherwise its vendor interface opened without taking it over; receiver slots that answered are remembered), other controllers through macOS's controller haptics (matched by name, or the only haptic controller connected). A request runs for its duration, at most 5 s without renewal, and a stop ends it at once. Tests: `Tests/BuildScripts/test_controller_rumble.py` (the built helper with a fake SDL and Wine driver: Wine's probe succeeds, an unplayable rumble is forwarded, a playable one stays with SDL), `ControllerRumbleTests`. **Not yet felt in a game.** Applies after Nokcandu restarts (new helper) and the game or launcher restarts.

### A profile used everywhere reaches Windows games' controller (November 13, 2026)

"Use a Profile Everywhere" used to switch Wine's controller driver off in every game, so only the profile's keys and mouse reached Windows games; what it made of the controller (remapped buttons, gyro as a stick, the emulated controller type) didn't. Found when a Steam Controller profile used everywhere (LT = RT plus gyro on, gyro as the right stick, emulated Xbox) gave Trackmania no gyro: the game saw the controller as Wine converts it, and the driver's status file was never written. Nokcandu now compiles the everywhere profile to `controller-profiles-everywhere.map` (before writing the flag, and whenever profiles are refreshed), and a game coming to the front names that map in `pad-active` instead of its own. Turning Everywhere off removes the map and games return to their own profiles. `pad-driver-off` and all profiles off still turn the driver off. A change applies when the game next comes to the front; an emulated controller type, when the game or launcher next starts. Test: `EverywhereProfileMapTests`. **Not yet tried in a game.**

### A profile that reads the controller itself is the controller games get (November 13, 2026)

With "Steam Controller, read directly" (formerly "Input controller → Steam Controller (2015 · USB / receiver)") Nokcandu reads the original Steam Controller itself, but its controller output (buttons, sticks, triggers, gyro as a stick, trackpads as sticks) only went to streams and Mac virtual controllers. Windows games got the raw controller as Wine converts it; after the Everywhere change above, Wine's driver also ran the same profile on that raw controller, which sees different inputs (no trackpad zones), so a carefully built profile came out mapped differently (reported in Trackmania). Rule now: a profile that reads the controller itself is the only source of that controller in games. Its compiled map carries `source steam`; Wine's driver (`padmap.m`, "Fed by Nokcandu") then opens `/tmp/nokcandu-padfeed-<uid>-<pid>.sock`, names it in the environment's `pad-feed`, drops the raw input of the Valve controller, and turns what Nokcandu sends (`PadFeed`: button/axis datagrams from the profile's engine while that Windows game is in front) into that controller's events, so the game sees the emulated controller (Xbox, DualShock 4 or Switch Pro) with exactly the profile's inputs. Nokcandu lets go of held buttons and axes when the game loses focus. Rumble from the game still reaches the trackpads (above). Tests: `Tests/BuildScripts/test_pad_feed.py` (the built helper as Wine's driver with a fake SDL: raw input dropped, a fed button delivered on the same device), `PadFeedProfileTests`. **Not yet tried in a game.** Applies after Nokcandu restarts and the game or launcher restarts.

**Game rumble** (Feedback in the profile editor): how strongly games' own vibration plays when Nokcandu plays it, 0–100 %, default 60 % (`Profile.gameRumble`); full strength on the Steam Controller's trackpads was reported as too aggressive.

### Controls tab: one sentence for what the game gets (November 13, 2026)

Four settings decided what a Windows game received (the environment's route, the profile's Emulated controller, Use a Profile Everywhere, the profile's controller input) and no screen showed the result. A game's Controls → Controllers now starts with **This game gets**: the connected controllers, what games see them as, the profile in effect (and whether it is used everywhere), the gyro, and rumble on the trackpads (`ControllerSummary`, tested by `ControllerSummaryTests`). When the profile sets an Emulated controller, the route row shows it ("Xbox controller, set by profile …" with Change…) instead of a choice it would override. A profile used everywhere is named on the game's Controllers and Controller Profile sections with **Stop Using Everywhere**. Device rows say what games see in plain words, and an original Steam Controller passed through as itself outside Steam Input offers **Use as an Xbox Controller**. Turning Everywhere on or off now also re-applies the environments' controller routes, and a profile used everywhere counts for the route (its emulated controller needs Wine's conversion).

- **The picture shows everything a button does** (November 13, 2026): a button with several outputs (LT as "Gyro on while held" + "LT") showed only the first; it now reads "Gyro + LT" (two at most, then "+n"). Steam trackpad zones show what their tap (or click) does instead of a dot, and directions set in a pad's existing behaviour (keys) show around its rim.
