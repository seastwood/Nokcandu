# Microphone permission during playback — 2026-11-02

## Confirmed regression and corrected conclusion

The user supplied a screenshot of Zero Hour running with Microphone Off while macOS requested microphone access for its native launcher. This supersedes the earlier inference that hiding endpoints and rejecting capture setup alone would prevent every visible prompt. Those guards remain necessary to block capture, including when macOS already has an Allow decision.

A process sample located playback initialization inside `AudioComponentInstanceNew`, before Wine's capture EnableIO call. The selected output device was a duplex virtual device. The same issue applies to other combined input/output devices; production code has no Jump Desktop name, UID or game exception.

Core Audio's component calls the deprecated `AudioDeviceGetProperty` family internally, bypassing interposition of the newer `AudioObjectGetPropertyData` family. Legacy input stream/default-input queries now receive the same Off policy. However, covering those calls alone did not eliminate the playback permission request.

Every generated app and wrapper also declared `NSMicrophoneUsageDescription` unconditionally. A fresh diagnostic app with that declaration absent initialized playback successfully and received macOS's automatic missing-declaration denial for microphone access, without a visible microphone dialog. The corresponding enabled-parent control reached the ordinary permission prompt. No existing TCC decision was reset or granted by the agent.

## Shared implementation

- New standalone apps default to no microphone declaration. `AppPrivacy` removes the old unconditional declaration from closed managed installations when their saved choice is Off, and restores it for explicit On. Unrelated metadata, saved preferences, content and launch scripts remain intact.
- Native-entry ownership records are updated with the same metadata change, including their Undo baseline. The helper hash and exact installed metadata must still match; manual edits and linked metadata/records are preserved. Launch preparation reports a failure visibly if it cannot safely apply the policy.
- Generated Wine app wrappers declare microphone use only for enabled games/clients. The existing endpoint/capture guard remains active independently of macOS consent.
- Battle.net-linked games now expose their existing per-game microphone choice directly, without exposing shared performance controls as if they were local.
- Before Play, shared clients receive the declaration for an explicitly enabled client or launching game, and for enabled games still running. An Off launch does not opt an otherwise disabled client in merely because a sibling has a saved On preference. Explicitly enabling or launching an On game prepares normal shared-client eligibility. A private intent marker distinguishes a deliberate opt-in from a legacy unconditional declaration. Cold client launches through game shortcuts also prepare the native client entry rather than depending on the client’s own Play button having been used. Once a live client session has opted in, its declaration stays until the client closes, preserving sibling access. An explicitly enabled shared client can legitimately request its own OS permission; Off games still cannot capture through the guarded APIs. macOS consent belongs to the responsible client identity, not a separate OS grant for every Windows child.
- On forwards the original input queries and capture setup. A previously denied OS permission is not reset: enabling the game does not override macOS Privacy & Security. Profiles do not grant OS consent; this policy is shared infrastructure, not a game-specific profile patch.

- Switch changes now rewrite the selected prefix's saved policy immediately, including its shared-prefix peers, instead of waiting for Play or periodic maintenance. `Tools/audio-guard/build-permission-probe.sh off /absolute/new-path.app` builds a fresh-identity manual regression app. It refuses an existing destination. The `on` variant preserves the declaration and may present the normal OS consent dialog; it never records audio. The diagnostic displays its result, writes a small temporary status log and exits when its window is closed. ## Comparisons rejected

Changing the audio unit from HAL Output to Default Output still reached a microphone check. Process input mute did not remove the request. A temporary private aggregate configured with zero input channels still exposed the source device's inputs, so it was destroyed and discarded. No audio-unit substitution, global device change, permanent sandbox policy, permission database edit or driver-specific workaround is part of the fix.

## Migration and Undo

Close/reopen a game to apply its saved microphone choice. Existing explicit On choices retain their declaration; Off installations lose the previous unconditional one. Shared clients retain enabled-session access until closed. Keep manually edited launchers unchanged and surface incompatible entry ownership instead of silently rewriting them.

Turning Microphone On restores normal eligibility and capture behavior on the next launch; existing macOS denial still requires a local Privacy & Security change. Reverting this code restores the older unconditional metadata behavior, not a previous OS consent state. Native-entry Undo retains the current microphone setting. No saves, game executables, network settings or selected audio devices are modified.

Sources: [Apple's HAL input setup note](https://developer.apple.com/library/archive/technotes/tn2091/) and [CurrentDevice property](https://developer.apple.com/documentation/audiotoolbox/kaudiooutputunitproperty_currentdevice). The observed permission timing and fresh-identity results above are local measurements, not promises made by those documents.
