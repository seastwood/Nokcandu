# ARM64 engine: state of things and plan (2026-11-20)

Follows [overwatch-and-arm64-wine-2026-11-05.md](overwatch-and-arm64-wine-2026-11-05.md), which made Nokcandu
recognise ARM engines (`EngineLayout`, `EngineVersion.arch`, `WineSelection.incompatibility`).

## Why now

- Rosetta: macOS 27 removes it on install (reinstallable); macOS 28 (autumn 2027) keeps it only for some older,
  unmaintained games, and whether Wine counts is unknown. An ARM engine has to be solid by then.
- macOS: CodeWeavers (Brendan Shanks, wine-devel, 2026-08-07): all the pieces for native ARM64 Wine are in macOS
  26.5 and later (an x18 custom ABI for Windows code, 4K pages for signed apps with the cross-architecture
  entitlement). CrossOver Preview ships ARM64 Wine with FEX (ARM64EC for x86_64, WoW64 for i386).
- Wine upstream: ARM64EC complete since 10.0; 11.20 relay debugging for ARM64EC; 11.22 AVX in the x86 emulation
  path. The macOS-ARM64 patches themselves were not merged as of 11.18 (no later news found).
- Graphics: DXMT builds ARM64EC/ARM64X in CI (Aug–Sep 2026). D3DMetal for ARM64EC not confirmed: D3D12 games may
  stay on Rosetta for a while.

## Prototype results (MetalSharp Wine 8.0, macOS 27.2.1, MacBook Air M4)

- Both 32-bit and 64-bit Intel programs run through FEX, no Rosetta (`Tools/arm-probe/bench.c`: the program sees
  native machine 0xAA64). Creating a Windows environment: 13 s (Intel engine under Rosetta: 16 s).
- CPU work, same program on both engines (ms, lower is better):

  | Test | 64-bit FEX | 64-bit Rosetta | 32-bit FEX | 32-bit Rosetta |
  |---|---|---|---|---|
  | Integer | 290 | 372 | 365 | 568 |
  | Floating point (sin, sqrt) | 2276 | 608 | 1334 | 4245 |
  | Memory copy | 66 | 76 | 64 | 78 |
  | 4 threads | 56 | 49 | 51 | 53 |

  FEX is as fast or faster except x87-style maths in 64-bit code (mingw's sin uses x87), about 3.7 times slower.
- Worms Armageddon (32-bit, DirectDraw) starts and draws its first-run dialog. The computer-use tool's clicks and
  keys don't reach Wine windows (as noted for the window driver), so play wasn't tested.
- **The engine has to stay exactly where and as it is.** Its loader has Apple's
  `com.apple.developer.cross-architecture-support` entitlement (needed for 32-bit games: 4K pages) through a
  provisioning profile of its makers' team. An APFS clone of the engine is killed by macOS (SIGKILL); a symlink to
  the untouched app works for both 32- and 64-bit programs.
- **Nokcandu's helper library can't load into it.** The engine uses the hardened runtime without
  `allow-dyld-environment-variables`, so DYLD_INSERT_LIBRARIES is dropped: no raw mouse, no Wine 11 app wrapper
  re-exec, and the per-game app wrapper (a copied loader) can't be used either.
- With the screen locked, Wine's first-time setup hangs (the Mac driver waits for the window server); tests that
  start Wine need an unlocked session.

## What Nokcandu has now (2026-11-20)

- `ExternalEngines`: sources (built-in MetalSharp; more can be added in Settings → Updates → Apple silicon
  engines as a GitHub repository and a file pattern, saved in `Engine Sources.json`), or an engine from a file
  (app, .zip, .tar.xz, folder). Downloads need a published SHA-256 (GitHub's digest or a SHA256SUMS file).
  The engine is unpacked untouched to `Runtimes/<id>/Engine/`; the runtime's `SharedSupport/wine` holds links
  (`bin`, `lib`, `share`) plus Nokcandu's `version` (`wine external <id> <wine version>`) and `engine.json`.
  A startup check (`cmd /c ver` in a throwaway environment) decides whether it can be chosen.
- `EngineVersion.external` carries the runtime id; such engines appear in each game's Wine picker (sorted below
  Sikarugir's builds of the same Wine version) and use the normal switch, trial and Roll Back.
- `EngineLayout.isSealed`: nothing writes into such an engine; the audio buffer setting refuses, the per-game app
  wrapper is skipped (games show as the engine in the Dock). The window driver and HID fix were already Intel-only.
- Tests: `ExternalEngineTests`; `ExternalEngineIntegrationTests` (off unless NOKCANDU_ENGINE_FILE and
  NOKCANDU_ENGINE_GAME are set) installs a real engine and switches a clone of a game to it and back.

## The open decision

Nokcandu's own ARM engine (with its window driver, helper library and native IPX built in) can be built without
Apple's paid developer program, but then only for 64-bit games. The cross-architecture entitlement that 32-bit
games need is honoured only through a provisioning profile and a signature of the profile's team. One project
(jdrly/gw2-on-mac #33, November 2026) reports it's a self-service capability on an App ID in the paid program
("Cross-architecture Compatibility Framework"); a developer on Apple's forums found free (Personal Team) accounts
can't get it. Until then, engines from other projects cover 32-bit games, without Nokcandu's in-engine features.

## Plan

1. **Prototype** (this session): run x86_64 and i386 test programs and one or two games on a prebuilt engine;
   compare start-up, frame rate and input against the Rosetta engine.
2. **Nokcandu's own pieces for ARM**:
   - `nokcandu-rawmouse.dylib` and the launcher are already universal (arm64 + x86_64).
   - The window driver (`Engine/winemac`) and native IPX's wpcap are x86_64 only: need `aarch64-unix` builds of
     the unix side and ARM64X builds of the Windows side, against the same Wine tree as the engine (the driver
     must match the engine's wineserver protocol, as `WindowedPresentation.serverRequestsMatch` checks).
3. **Our own engine build** (CI): one patched Wine tree (the macOS-ARM64 patches + Nokcandu's driver patches),
   FEX for ARM64EC and WoW64, DXMT ARM64X; signed with the cross-architecture entitlement so i386 games work.
   Prebuilt third-party engines are fine for testing but tie the driver patches to someone else's tree.
4. **In the app**: ARM engines offered per game as a preview, Rosetta stays the default; the Wine picker shows
   which games an ARM engine can't run (`WineSelection.incompatibility`).

## Worms Armageddon on MetalSharp 8.0 (evening, 2026-11-20)

Verified, in order:

1. **Crash at start (stack overflow at address 0):** the prefix kept `HKLM\Software\Microsoft\Wow64\x86` =
   `wow64cpu.dll` from the Intel engine (`wineboot -u` keeps it), so 32-bit code ran with no emulator. Fixed for
   every switch: `EngineUpdate.setWow64Emulators` writes the keys from `EngineLayout.wow64Emulators`.
2. **Fatal error 0x80000100:** MetalSharp gives new prefixes `syswow64/winemetalgl.dll` (and others) that
   `wineboot -u` doesn't add to existing ones. Fixed for every switch: the engine's self-test records which
   system files come from the engine (`system-files.json`), and a switch adds the missing ones (never replaces).
3. **Fullscreen at 1920×1200 gave a black box in a grey screen:** the engine's own Mac driver can't change the
   display's resolution, and Nokcandu's resizable window (its own driver) was Intel-only.

### Nokcandu's driver for MetalSharp (winenokmac)

- The engine is signed (cross-architecture entitlement through a provisioning profile), so its files can't
  change. It does carry `com.apple.security.cs.disable-library-validation`, so an ad-hoc signed driver loads.
- Wine finds builtin modules in the engine's own directory first (`dll_dir`, then `WINEDLLPATH`), so a driver
  named `winemac` can't replace the engine's. Nokcandu's is `winenokmac.drv`/`winenokmac.so`
  (`Engine/winemac/build-metalsharp.sh`: MetalSharp's Wine source at the release's commit,
  `patches-metalsharp-8.0`, which is the Wine 11 driver series merged three-way onto MetalSharp's driver).
  `"Graphics"="nokmac,mac"` in `HKCU\Software\Wine\Drivers` picks it, with the engine's driver as fallback.
- Wine loads a builtin that has no file in the prefix only while the prefix is being created
  (`find_builtin_without_file`), so the Windows halves also go into `system32`/`syswow64`. The unix half is
  found only through `WINEDLLPATH`: the launcher gets it from `perf.env` (`WindowedPresentation.armEnvLine`),
  Nokcandu's own Wine tools from `WindowedPresentation.addEnvironment`.
- MetalSharp's `winemetal.so` (DXMT) links `@rpath/winemac.so`, so a D3D10/11 game would load the engine's
  driver next to Nokcandu's (two copies of the Cocoa classes). Not yet tested; OpenGL/D3D9 games don't load it.
- MetalSharp's WineMetalGL (its `opengl32`) draws into Wine's client view when the driver exports
  `macdrv_functions`, otherwise into a view of its own placed from Win32 coordinates, which doesn't match a
  scaled window (black picture). The ARM build exports a table with Wine 11's window data layout and gives a
  top-level window a client view when WineMetalGL asks for one (`d3dmetal.c`, aarch64 part).
- Started outside Nokcandu's launcher, Wine windows get no keyboard or mouse; test with **Play**.
