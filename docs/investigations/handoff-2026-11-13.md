## Open issue: Steam Controller trackpad jitters while the thumb moves

**User's words:** "Now it only jiggles while I move my thumb on the trackpad. Stays still while still." They want
it solved **without any added latency**: "This must be a very responsive trackpad."

### Setup

- Original 2015 Steam Controller on its USB cable (28de:1102), read directly by Nokcandu ("Controller input →
  Steam Controller, read directly", `controllerSource = steamUSB`). Path: `SteamControllerUSB` (IOKit, the vendor
  interface) → `SteamControllerReport.decode` → `DesktopPad` (around line 610) →
  `PadSteamTrackpad.touch(down:x:y:at:settings:)` with x = (rawX/32767+1)/2, y = (1−rawY/32767)/2 →
  `steamPadMouse` → pointer, and `SteamControllerUSB.movementFeedback` (movement haptics, around line 628).
- The user's profile "Steam Controller", right trackpad: mode `trackball`, `smoothing: 0`, `steadiness: 0`,
  `sensitivity` 647, `sensitivityX` 1335, `sensitivityY` 1404 (pixels per full pad), `rotation` −21.9°,
  `halfLife` 0.094, movement haptics on (`movementFeedback` 0.19, `hapticRate` 12.8 Hz, `hapticSpacingMS` 0.175,
  follows movement), `touchFeedback` 0.38. Profiles live in
  `~/Library/Application Support/Nokcandu/controller-profiles.json` (back it up before touching it).

### Evidence

- `docs/investigations/data/steam-right-pad-2026-11-13.txt`: 2,045 input reports with the right pad touched,
  recorded read-only alongside Nokcandu at about 125 reports/s (columns: seconds, sequence, rightTouch, unused,
  rightPadX, rightPadY, gyro x/y/z; pad values −32768…32767, y up). It has resting stretches and movement.
- Record more with `Tools/controller-probe/steam-trackpad-recorder.c` (build line in its header; it sends nothing
  to the controller, and the user is happy to perform movements while you record).
- Measured: under a **still** thumb the readings scatter about 0.003–0.0045 of the pad around their mean (single
  readings up to 0.014), in steps of 66 (x) and 98 (y) raw units. While **moving**, the scatter around a straight
  line fitted over 64 ms is about 0.0045 at slow speeds and 0.006–0.01 at 1.5–2.5 pads/s. At the user's
  sensitivity that is roughly 6–13 px of jitter per report. A replug did not change the noise, so it isn't a
  firmware calibration fault.

### What was done (and works)

The original symptom was a jiggle and continuous buzz **while resting**, sometimes. Cause: "resting" was judged
from an instant speed the noise kept high, and the trackball also waited for its own momentum, which the noise
kept alive; the movement haptics then shook the pad further. Fixed in `PadSteamTrackpad`:
- resting is judged on the average position over 80 ms windows (`restWindow`, `drift(now:)`);
- leaving rest stays instant: one reading beyond `noiseMultiple` (5) × the pad's current scatter around the
  finger's straight-line path (`scatter(_:)`), floored at the old `landingDistance` 0.008 and capped at 0.03,
  releases the cursor on that report, so a quiet pad behaves exactly as before;
- the trackball momentum condition is gone.
User confirmed: still while still. Tests: `TrackballRestTests.swift` (synthetic wobble, start-from-rest under
50 ms, and `RecordedRestingThumbTests` replaying `RestingThumbRecording.swift`), plus the existing
`SteamPadFeelTests`/`SteamPadSteadinessTests`, which must keep passing unchanged (they encode the feel the user
tuned earlier). Details: `docs/engineering-learnings.md`, "Judge a resting finger against the pad's own noise".

### What's left, and leads

While moving, every reading goes to the cursor unfiltered (smoothing 0), so the pad's noise rides on top of the
motion. Constraints: no perceptible latency; the existing feel tests define acceptable behaviour; the fix must be
shared (every pad, every profile), not tuned to one user.

1. **Check the haptics first.** Movement haptics fire while moving and shake the pad. Ask the user to turn off
   *Movement haptics* for the right pad and compare, or record with them on and off. If the jitter mostly goes,
   the fix may be suppressing or discounting readings for a few ms after each pulse (Nokcandu knows when it sent
   one) rather than filtering.
2. **The existing smoothing can't cope with this noise.** With `smoothing` > 0 the cutoff is
   `25·0.1^s + 80·speed`, where speed is a 15 Hz low-pass of the raw per-report velocity; this pad's noise alone
   reads as about 0.5 pad/s, which opens the filter to about 50 Hz, so it removes little. A speed estimate that
   noise can't inflate (from a short least-squares fit, or the One Euro filter's filtered derivative) would let
   real speed open the filter while jitter doesn't. The One Euro filter is the standard low-latency answer.
   Measure added lag on a swipe; `testAFastSwipeArrivesInFullAndPromptly` allows only a few ms.
3. The coarse quantization (66/98 units) is part of the noise; a filter that respects it (hysteresis of about one
   step per axis while moving slowly) is another option, but `steadiness` (a per-axis dead band) was rejected
   before: it stalled mid-swipe and hooked sideways (see the comments in `PadSteamTrackpad`).
4. Valve's own driver applies smoothing on the controller (`SETTING_SMOOTH_ABSOLUTE_MOUSE`, settings tag 24 in
   SDL's `controller_constants.h`) when the pad is in absolute-mouse mode. Nokcandu sets both pads to
   `TRACKPAD_NONE` (`SteamControllerMode.captured`), so no firmware smoothing applies. Unverified whether that
   setting affects raw report coordinates in that mode; don't write untested settings to the user's controller
   without asking.

Rejected so far: a fixed higher release threshold (delays every small start); averaging before leaving rest over
80 ms or 4 reports (cost 1–2 reports on slow starts and failed the feel tests).

  keyboard and mouse, pairing (also against a fake host), sound.

  failed check no longer drops a pairing (`recoverPairing`), Mbed TLS 3 CBC padding patch (audio), output engine

- Features: End Stream / End and Quit (Stream menu, ⌃⌥⇧ shortcuts), "No controller", settings applied mid-stream
  (`StreamWindowController.apply`), output device (default follows macOS), bitrate, frames to buffer, Game Mode

  stream in the header's Running strip, "Emulated controller type" naming (Automatic/Xbox/PlayStation/Switch

### Emulated controllers — `docs/controller-capabilities.md`
- A profile's **Emulated controller** (None/Xbox/DualShock 4/Switch Pro) applies to Windows games, streams and
  (once entitled) Mac apps. Shared protocol core `Sources/NokcanduPadEngine/virtualpad.c` (one copy, also built
  into Wine's driver via `Engine/controller-hid/0004-controller-emulation.patch` + `controller-emulation.h`).
  **Verified**: DS4 and Pro appear correctly to Windows inside Wine 11 (probe in an environment). *Built*: real
  games and emulators using them. Wine 10 dropped from scope.
- Mac apps: CoreHID `HIDVirtualDevice` (`MacVirtualController.swift`), gated on Apple's
  `com.apple.developer.hid.virtual.device` entitlement, which needs the user's paid developer account (their
  choice). `build-app.sh` adds the entitlement only when `NOKCANDU_PROVISIONING_PROFILE` grants it.
- **Profile-fed controller** (`PadFeed.swift`, "Fed by Nokcandu" in `Resources/rawmouse/padmap.m`): a profile that
  reads the controller itself compiles `source steam`; Wine's driver then drops that controller's raw input and
  presents Nokcandu's mapped output as the emulated controller. Fixes inputs mapped twice and differently
  (reported in Trackmania). Test: `test_pad_feed.py`. *Built*, not yet confirmed in game.
- **Use a Profile Everywhere** now reaches Windows games' controller (`controller-profiles-everywhere.map`); it
  used to switch Wine's driver off, so gyro-as-stick and remapped buttons never applied. Turning it on or off
  re-applies the environments' controller routes.
- **Rumble on controllers SDL can't rumble** (`ControllerRumble`, `ControllerRumbleRouter`, helper hook of
  `SDL_JoystickRumble`): played on the Steam Controller's trackpads or via macOS haptics. **Verified** in
  Trackmania (user: works, too strong). Per-profile **Game rumble** strength (default 60 %, Feedback section).
- Controls tab rework: "This game gets" summary (`ControllerSummary`), route row shows a profile's emulated
  controller instead of an overridden picker, Everywhere shown with Stop, plain device descriptions, "Use as an
  Xbox Controller", source renamed "Steam Controller, read directly (trackpads, haptics)", route title says its
  scope ("Controllers in Steam games" etc.), stick choices name the stick ("Left stick", "Right stick
  (swapped)"), the picture shows combined outputs ("Gyro + LT") and trackpad zone labels. *Built*; the user saw
  some of it.

### Fixes
- **Profiles disappeared** (all nine): one binding (`pad:lptap`, a trackpad tap set to Tap/Hold) was written but
  rejected on reading, and a failed read showed as an empty library. Now read leniently (unknown output →
  Nothing, original kept as `controller-profiles.json.unreadable-backup`), never written unreadable, and Tap/Hold
  no longer seeds a virtual input with itself. **Verified**: the user's profiles came back.
- **Trackmania "free up 5 GB … page_file/committed memory"**: Wine counts only free + inactive memory plus unused
  swap, and macOS swap grows on demand. The helper (`Resources/rawmouse/commit-memory.c`) reports swap able to
  grow to RAM size (never into the last 10 GB of disk), for every Wine environment; `NOKCANDU_MACOS_SWAP=1`
  undoes it. Replacing `ntdll.so` was rejected (the engines are Sikarugir builds with msync). *Built*.
- Trackpad resting jiggle (above). **Verified** by the user.
