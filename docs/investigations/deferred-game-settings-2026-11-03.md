# Save settings without forcing a restart — 2026-11-03

## Confirmed problem and corrected interpretation

The shared `AppModel.changeSetting` path previously offered only Apply and Restart or Cancel. It coupled saving desired values to stopping/reopening an entire Windows environment. The user reported this for Wine on a closed Falconeer game and for other settings. `WineTools.environmentIsRunning` also treated any failed/slow 0.3-second `wineserver -w` probe as running. That conflates a slow command, idle infrastructure and actual gameplay; an owned native process must still be respected.

The new settings path never asks to restart, closes an active game, or reopens a closed game. Existing explicit restart commands and their unsaved-progress confirmations remain available. The earlier restart-only flow documented in settings/engine investigations is superseded for ordinary setting saves.

## Shared behavior

`PendingSettings.Change` is a typed, Codable request for Wine, graphics, launch options/program changes, performance/frame cap, buffer, display/window style, recipe/hosted settings, IPX adapter/frame, and compatibility/cinematic install/Undo. Saving a request is separate from applying it. The newest request for the same game/setting replaces the older one. Other setting choices remain independently saved. Game pages show **Saved for Next Start**, requested values and any application error, with Discard Pending Changes. Discard does not undo already applied settings or touch game content.

The core uses a fresh, reliable process scan for mutation decisions; the periodic UI retains its existing cache. Known Wine infrastructure can be stopped quietly when no interactive program remains. Unknown state or an active game/client/installer defers application. Windows cmd/tools and unrecognized processes are not treated as disposable services. PID lock files also require ownership evidence, so a reused PID cannot identify an unrelated program as the game. A closed game is not reopened after changing its settings.

Microphone and raw-mouse controls that already work live keep their existing immediate path. They do not wait in the queue; a later queued configuration preserves the current microphone choice. Steam/Battle.net/other hosted games retain the actual Windows host scope. A shared client that stays open may need its next full shutdown/start before queued environment changes apply; saving does not force that shutdown.

## Persistence, icons, migration and failure recovery

Requests live under Nokcandu's Application Support **Pending Settings**, outside running game bundles. A live disposable-clone test returned EPERM when creating new state inside its active .app; moving requests outside the app resolved the test. The exact macOS policy responsible was not traced, so it is not attributed to a specific permission mechanism. Requests are associated with a canonical host path and game identity. Moved private apps can find their prior requests when the old location is gone and identity matches; an existing different copy's queue is not adopted.

The generated native app entry invokes `nokcandu-settings` before its existing shell script starts Wine. It uses the same queue/application path as Play in Nokcandu, including shared hosts. The small helper is shipped/signed with the app, recorded by checksum and included in Repair. Existing recognized generated entries migrate; manual scripts/edited entries are preserved. Older/manual entries without the hook require a launch through Nokcandu to apply their requests. The UI states that limitation when the helper is absent. Queuing itself does not require modifying a running game app.

An application-only cross-process lock prevents duplicate execution. Saving another choice does not wait for that lock. App-icon/Play preflight waits for an already applying transaction rather than launching into half-replaced files. A request superseded during application is not lost or mistaken for an error. Wine choices are prepared/verified before being queued, and their runtime caches are protected from unused-cache cleanup. Per-action existing ownership checks and exact engine rollback remain intact.

Failures retain their requests and a local diagnostic for visible retry/discard. Corrupt/linked metadata is preserved, not followed or silently deleted. Requests for a disconnected app drive defer without blocking unrelated games; missing/mismatched identities report an error rather than targeting another installation. No game files/saves are removed by saving/discarding requests. Undo an applied engine with the existing rollback or a component with its existing Undo. Pending requests are local intent, not machine-specific files to export in a shared profile.

## Validation and useful unsuccessful comparisons

Seventeen isolated queue tests cover deferred active/unknown sessions, idle-service handling without reopen, actual performance application, persistent/coalesced values, moved apps, live microphone preservation, stale PID ownership, retry/discard, concurrency, updates during application, native-entry application before the script, corrupted/linked metadata, inactive status without launching a probe, and offline pending apps. Temporary-path `/var` versus `/private/var` aliases initially triggered an overbroad symlink check; checks now validate leaf links and canonical owned directories instead of comparing aliased URL objects.

The real-Wine test uses a disposable game clone and a long-running Windows command. Saving Wine 10.0 while it is active leaves the current engine unchanged and request pending. After explicitly closing only that temporary session, applying the request succeeds, the game stays stopped, and rollback restores the prior engine hash. It passed after moving state outside the live bundle. Existing restart tests were updated to reject the slow-probe false positive; a real owned orphan still registers as active through a fresh scan and unrelated processes survive explicit shutdown. The first complete suite exposed those two obsolete/stale-snapshot assumptions; both targeted regressions then passed.

Final verification: all 317 tests passed (13 optional integration skips); the explicit real-Wine deferred-selection/rollback test passed separately. The production app built and passed deep strict signature verification before and after installation. Preview and installed UI opened on Falconeer with its original Wine 10.0 r8 intact, a Play button and no forced-restart dialog.
